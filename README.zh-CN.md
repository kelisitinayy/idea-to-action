# idea-to-action · 想法落地教练

> 把「我想做……但不知道从哪开始」变成第一个能用的成果。

一个可移植的 Agent 技能——只有一份 `SKILL.md`，无运行时、无依赖——面向有愿望但缺领域知识、
不熟悉工具生态、也说不清第一步该做什么的用户。

**English → [README.md](README.md)**

---

## 它解决什么问题

大多数 Agent 技能默认你已经知道自己要做什么，只差执行。它们恰好卡在更早的那一步：**用户有的是愿望，不是需求。**

让这类用户「先把需求写清楚」，得到的通常是沉默，或者一份抄来的、自己都不信的需求。
真正有效的顺序是反过来的：

1. 先问几个用户**答得上来**的问题；
2. 去查这个领域的人**实际是怎么做的**；
3. 摆出 2—3 条有真实成本的路径；
4. 让用户按**结果**选，而不是按技术选；
5. 一起做最小的完整一件；
6. 用用户自己的样例验证。

这个技能就是这套顺序。

## 六个阶段

| 阶段 | 产出 |
|---|---|
| 1. 第一段访谈 | 目标、现在的做法、真正卡住的环节、现实限制 |
| 2. 主动调研 | 真实案例、成熟软件、开源项目、技能与连接器——带原始链接和查证日期 |
| 3. 案例 + 第二段访谈 | 2—3 条有实质差异的路径，各含投入、成本、自动化程度和缺口 |
| 4. 制作方案 | 一个小而完整的第一版成果、验收标准、实施顺序、分工 |
| 5. 陪跑制作 | 优先复用已有能力，只在卡住结果的地方补缺口 |
| 6. 验收与续接 | 哪些通过、哪些未验证、下次怎么复用 |

较长的任务还会维护一份精简记录，中断后不必让用户再讲一遍。

## 设计原则

- **事实由 AI 查，偏好由用户选。** 能自己查到的，不反过来问用户。
- **先复用，再自建。** 比较免费/开源、上手难度、自动化程度和维护成本之后，才说「我们自己写」。
- **四态分离**——建议、已生成、已安装、已运行、已验证，没有证据不说「完成」。
- **不承诺无法验证的结果。** 播放量、转化、收入从来不是「做出来」就证明了的事。
- **尊重用户已做的选择。** 用户说要 Agent，不要擅自换成表格——先问清底层目标，再决定保留还是明确重谈。
- **每轮问 1—3 个问题**，按决策依赖推进，不做问卷。

## 安装

### 通过 skills.sh

```bash
npx skills add kelisitinayy/idea-to-action
```

### 手动安装

```bash
git clone https://github.com/kelisitinayy/idea-to-action

# 按你用的宿主选一个或多个
cp -r idea-to-action/skills/idea-to-action ~/.claude/skills/
cp -r idea-to-action/skills/idea-to-action ~/.codex/skills/
cp -r idea-to-action/skills/idea-to-action ~/.dsh/skills/
```

适用于任何读取 `SKILL.md` 目录的宿主：Claude Code、Codex、DeepSeek Harness 及兼容 Agent。
技能自包含，**不要求预装** `grilling` 或其他技能。

## 示例

```text
> 我做电商，想做抖音，不知道怎么开始

< 我的初步理解是，你希望用短视频帮助商品销售，但还没有确定内容形式。
  我先了解三个会直接影响方案的事：
  Q1 你的商品是什么、单价大概多少？
  Q2 你能出镜吗，还是只能拍商品？
  Q3 每天能投入多长时间？
  这三点定了，我去找几种真实跑通的做法给你看，而不是先给你一堆工具。
```

## 诚实的边界

- 方法论正文是**中文优先**。英文描述是为了被检索到，英文用户能拿到结构，但还没有英文版完整方法。
- 假设宿主具备联网搜索能力。没有时技能会明说，并退化为纯访谈，而不是编造搜索结果。
- 它是一套教练方法，不是自动化引擎——它不会替你交付产品。
